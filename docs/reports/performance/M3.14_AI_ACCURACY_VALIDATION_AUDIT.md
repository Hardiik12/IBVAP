* **Tracker Configuration:** `bytetrack.yaml` (integrated Ultralytics ByteTrack).

  - Two-stage data association: Associates high-confidence detections first, then low-confidence detections ($0.1 \le \text{conf} < 0.35$) using Kalman filter spatial trajectory estimation.

## E. Polygon Zone & Spatial Containment Logic

* **Source File:** [`ai/zones/engine.py`](file:///Users/hardik/Downloads/IBVAP/ai/zones/engine.py)
* **Polygon Representation:** List of normalized 2D vertices `[[x1, y1], [x2, y2], ...]`, where $0.0 \le x_i, y_i \le 1.0$.
* **Reference Point Definition ([ADR-004](file:///Users/hardik/Downloads/IBVAP/docs/specs/DECISIONS.md#L33-L38)):**
  $$\text{Reference Point} = \left( \frac{x_1 + x_2}{2}, \; y_2 \right) \quad \text{(Bottom-Center / Foot Point)}$$
  - *Design Rationale:* In ground-plane perimeter monitoring, the bottom-center of the person bounding box represents where the subject's feet touch the terrain. This prevents false alarms caused by raised arms, shadows, or hats crossing the perimeter line before physical ground penetration.
* **Containment Algorithm:** `cv2.pointPolygonTest(polygon_contour, (x_foot, y_foot), measureDist=False)`
  - Returns `+1` (Inside), `0` (On Boundary), `-1` (Outside).
* **Resolution Independence:** Fully resolution-independent across 720p, 1080p, and 4K streams due to normalized coordinate geometry.

## F. Intrusion State Machine & Duplicate Suppression

* **Source File:** [`ai/events/engine.py`](file:///Users/hardik/Downloads/IBVAP/ai/events/engine.py)
* **State Machine Evaluation per `(zone_id, track_id)`:**

```text
       ┌──────────────┐
       │   OUTSIDE    │ ◄──────────────────────────────┐
       └──────┬───────┘                                │
              │                                        │
   Foot point enters polygon                           │
    (OUTSIDE -> INSIDE)                                │
  [EMIT 1 INTRUSION EVENT]                             │
              │                                        │
              ▼                                        │
       ┌──────────────┐                       Foot point exits
       │    INSIDE    │                       (INSIDE -> OUTSIDE)
       └──────┬───────┘                       [RESET STATE TO OUTSIDE]
              │                                        │
   Consecutive evaluations                             │
     (INSIDE -> INSIDE)                                │
  [DUPLICATE SUPPRESSION]                              │
      (0 events emitted)                               │
              │                                        │
              └────────────────────────────────────────┘
```

| Transition | State Change | Decision | Events Emitted |
| :--- | :---: | :--- | :---: |
| **Initial Entry** | `OUTSIDE` $\rightarrow$ `INSIDE` | **Positive Edge Intrusion** | 🟢 **1 Event Emitted** |
| **Stationary / Walking in Zone** | `INSIDE` $\rightarrow$ `INSIDE` | Duplicate Suppression ([ADR-007](file:///Users/hardik/Downloads/IBVAP/docs/specs/DECISIONS.md)) | ⚪ **0 Events (No Spam)** |
| **Zone Exit** | `INSIDE` $\rightarrow$ `OUTSIDE` | State Reset | ⚪ **0 Events** |
| **Re-entry** | `OUTSIDE` $\rightarrow$ `INSIDE` | Second Intrusion Edge | 🟢 **1 New Event Emitted** |

## M. Known AI Limitations (Empirically Honest)

1. **Resolution Constraints:** Standard 640x640 inference may fail to detect distant human targets smaller than $20 \times 20$ pixels at ranges $>80\text{ meters}$.
2. **Illumination Dependencies:** Standard COCO RGB weights experience degraded recall in pitch-black night scenarios without thermal or IR illumination.
3. **Occlusion Duration Horizon:** ByteTrack retains lost tracks for ~30 frames. If a subject remains hidden behind a bunker or vehicle for longer, a new Track ID is generated upon re-emergence.
4. **Camera Movement Assumption:** Virtual polygon geofences assume a stationary camera. If a Pan-Tilt-Zoom (PTZ) camera moves, polygon coordinates require dynamic homography or recalibration.

## N. SIH Judge Questions & Technically Honest Answers

### 1. "What is your detection accuracy?"
> *"Our system uses Ultralytics YOLOv8n, which achieves **37.3% mAP50-95** on standard COCO benchmarks. In our current SIH MVP, we focused on end-to-end integration and throughput (**185+ FPS** and sub-6ms per-frame latency). We do not claim a fabricated local accuracy percentage because our repository does not yet include a domain-specific annotated ground-truth dataset. Our pipeline software correctness is verified across 187 automated tests."*

### 2. "How did you evaluate YOLO?"
> *"We evaluated YOLO through: (1) Unit tests for coordinate normalization and class filtering; (2) Fail-closed SHA-256 weight integrity validation; and (3) End-to-end video pipeline benchmarks over 300 frames of real video."*

### 3. "Why YOLOv8n?"
> *"Border security edge devices operate under constrained compute and thermal budgets without high-end GPUs. YOLOv8n offers the ideal Pareto trade-off: **185+ FPS on standard CPU hardware** while maintaining robust human detection."*

### 4. "Why ByteTrack?"
> *"Traditional SORT drops low-confidence boxes during occlusion, causing frequent track ID switches. DeepSORT adds heavy ReID neural network inference that throttles CPU frame rates below 30 FPS. ByteTrack leverages Kalman motion prediction to associate occluded boxes without ReID overhead, maintaining 185+ FPS."*

### 5. "How do you prevent duplicate alerts?"
> *"Our Intrusion Event Engine implements **ADR-007 Duplicate Suppression**: it evaluates `(zone_id, track_id)` state transitions and triggers exactly one alert on the positive edge (`OUTSIDE` $\rightarrow$ `INSIDE`). Continuous presence in the zone produces zero duplicate alerts."*

### 6. "How do you determine someone entered a restricted zone?"
> *"We implement **ADR-004 Foot-Point Reference Math**: we evaluate containment at the bottom-center point $(\frac{x_1+x_2}{2}, y_2)$ using OpenCV point-in-polygon ray-casting. This represents where the subject's feet touch the ground, eliminating false triggers from raised arms or shadows."*

### 7. "What happens with multiple people?"
> *"ByteTrack maintains distinct Kalman-filtered Track IDs for each person. The state machine tracks each `(zone_id, track_id)` independently, firing distinct alarms for each individual entering the zone."*

### 8. "What happens during occlusion?"
> *"ByteTrack keeps lost tracks in a buffer for up to 30 frames. When the person steps out from behind an obstacle, ByteTrack re-associates the detection with the existing Track ID rather than creating a duplicate alarm."*

### 9. "What happens at night?"
> *"Standard RGB models require visible light or IR/thermal illumination. For complete night vision, the post-MVP roadmap integrates fine-tuned thermal/IR model weights."*

### 10. "What happens if the person is far away?"
> *"Distant persons smaller than 20 pixels may fall below the 0.35 confidence threshold on 640px input. In production, we deploy higher-resolution input (1280px) or optical zoom cameras."*

### 11. "How do you handle false positives?"
> *"False positives are mitigated by: (1) Setting confidence threshold to 0.35; (2) Filtering exclusively for target classes (`person`, `car`, `truck`); (3) Evaluating bottom-center ground contact points; and (4) Requiring track temporal persistence."*

### 12. "How would you improve accuracy in production?"
> *"We would fine-tune YOLOv8 on a labeled border-surveillance dataset containing military camouflage, varied terrain, thermal/IR feeds, and severe weather conditions."*

### 13. "Can the system support multiple cameras?"
> *"Yes. The architecture associates each camera stream with a unique UUID, evaluating polygon zones and dispatching events independently per camera channel."*

### 14. "What is currently proven versus future work?"
> *"**Proven:** 185+ FPS CPU pipeline, ByteTrack tracking, foot-point PIP containment, duplicate suppression, live WebSocket alerts, Argon2id RBAC, and SHA-256 evidence hashing. **Future Work:** Labeled border benchmark dataset, thermal/IR model fine-tuning, and multi-camera load balancing."*
