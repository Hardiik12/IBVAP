## A. Executive Summary

A comprehensive repository-wide audit was conducted across the IBVAP codebase, database models, storage services, scripts, and documentation to assess current **Backup & Restore** capabilities.

### Key Audit Findings:
1. **No Automated Backup/Restore Executables:** There are currently **no automated backup scripts** (e.g., `pg_dump` wrappers, evidence archiving utilities, or automated restore scripts) in `scripts/`, `backend/`, or `integration/`.
2. **"Backup" in Existing Code/Docs Means Contingency Planning:** Existing references to "backup" in documentation (`SIH_DEMO_BACKUP_PLAN.md`, `DEMO_CHECKLIST.md`) refer strictly to presentation failure contingency tiers (Level A Live Webcam $\rightarrow$ Level B Video Benchmark $\rightarrow$ Level C Slide Deck).
3. **"Restore" in Existing Code Means Single-File Tamper Recovery:** References to "restore" in test suites (`test_evidence_integrity.py`, `test_e2e_pipeline.py`) and scripts refer to reversing a simulated 1-byte file mutation during forensic tamper demonstrations, or re-seeding the demo database via `backend/app/db/seed.py`.
4. **Data Persistence Mechanisms Exist:** Docker volume persistence (`postgres_data`) and local disk persistence (`data/evidence/`) reliably preserve data across server restarts, but do not provide portable, point-in-time disaster recovery.
5. **Forensic Hashing Infrastructure is Present:** Server-authoritative SHA-256 hashing and tamper detection are fully operational at the individual evidence record level, providing the cryptographic foundation required for a future backup manifest.

## E. PostgreSQL Database Assessment

1. **Active Database:** `ibvap` on `127.0.0.1:5432` (PostgreSQL 18.3 UTF-8).
2. **Schema Scope:** All 7 core tables (`users`, `cameras`, `zones`, `events`, `alerts`, `evidence`, `audit_logs`) + `alembic_version`.
3. **Relational Constraints:**
   - Primary keys on all tables.
   - Foreign key `evidence.event_id` $\rightarrow$ `events.id` with `ON DELETE RESTRICT` (ensures evidence records cannot be orphaned).
   - Foreign keys with `CASCADE` on `zones` and `alerts`.
4. **Native Backup Command (Manual):**
   ```bash
   pg_dump -h 127.0.0.1 -p 5432 -U postgres -d ibvap -F c -b -v -f ibvap_backup.dump
   ```
5. **Native Restore Command (Manual):**
   ```bash
   pg_restore -h 127.0.0.1 -p 5432 -U postgres -d ibvap -v --clean ibvap_backup.dump
   ```

## G. SHA-256 & Forensic Integrity Assessment

1. **Individual Record Hashing:** Fully operational. Every evidence record in PostgreSQL stores a 64-character hexadecimal SHA-256 digest computed server-side (`hashlib.sha256`) in 64KB chunks.
2. **Tamper Verification:** The backend re-reads physical disk bytes upon request (`GET /api/v1/evidence/{id}/verify`), recomputes SHA-256, and returns `VERIFIED` or `MISMATCH`.
3. **Missing Manifest Capability:** There is no batch export utility that compiles all evidence file paths, sizes, and SHA-256 checksums into an external `manifest.json` for post-restore verification.

## H. Security & Secret Protection Assessment

Any future backup implementation must strictly adhere to the following security boundaries:

1. **Sensitive Data in Database Dump:**
   - `users.password_hash` contains Argon2id password hashes.
   - `users.mfa_secret` contains Base32 TOTP secrets.
   - `users.face_embedding` contains biometric vectors.
   - `audit_logs` contains sensitive security event telemetry.
2. **File Permissions & Storage Protection:**
   - Backup directory `backup/` and all `.dump` / `.tar.gz` archives MUST be added to `.gitignore` to prevent accidental credential commits.
   - Backup archives must be written with restricted permissions (`chmod 600`).
3. **Zero Secret Leakage in Manifests:**
   - `manifest.json` must record ONLY public metadata (file names, sizes, timestamps, SHA-256 hashes, row counts).
   - Plaintext passwords, JWT secrets, and API credentials must NEVER be written to backup manifests.

## K. Recommended Minimal Architecture (For Future Implementation)

If backup/restore is implemented, it should follow a self-contained, standalone script approach without modifying core backend or AI pipeline code:

```
backup/                               # Root backup storage directory (git-ignored)
└── ibvap_backup_YYYYMMDD_HHMMSS/
    ├── database/
    │   └── ibvap.dump                # Custom-format pg_dump binary archive
    ├── evidence/
    │   └── <snapshot files>          # Archived evidence frame images
    ├── manifest.json                 # Cryptographic SHA-256 manifest of all evidence files
    └── metadata.json                 # Backup metadata (timestamp, table row counts, version)
```

## L. Proposed Script File Structure

1. **`scripts/backup.py`**:
   - Executes `pg_dump` via `subprocess` against configured `DATABASE_URL`.
   - Copies `EVIDENCE_ROOT` snapshots to the backup directory.
   - Computes SHA-256 digests for all evidence files and writes `manifest.json` & `metadata.json`.
2. **`scripts/restore.py`**:
   - Reads target backup directory.
   - Restores PostgreSQL schema and data via `pg_restore`.
   - Restores evidence files to `EVIDENCE_ROOT`.
   - Iterates through `manifest.json` to verify that 100% of restored evidence files match their cryptographic SHA-256 hashes.

## M. Testing Strategy (When Implemented)

1. **Backup Execution Test:** Verify backup creates `database/ibvap.dump`, `evidence/`, and valid `manifest.json`.
2. **Restore Execution Test:** Restore into a dedicated test database (`ibvap_test`) and verify table counts match metadata.
3. **Cryptographic Integrity Test:** Verify all restored evidence files match `manifest.json` SHA-256 hashes.
4. **Tamper Detection Test:** Intentionally modify 1 byte in a restored evidence file and confirm the restore validator flags `TAMPER DETECTED`.
5. **Missing File Test:** Intentionally delete 1 restored evidence file and confirm validator flags `FILE MISSING`.
6. **Secret Exclusion Test:** Confirm zero plaintext passwords or secrets in `manifest.json` and `.gitignore` includes `backup/`.

* **Storage Footprint:** Large video evidence folders could consume significant local disk space if backups are not pruned.
